## 상세 구현 지침

### `5.6` 처리 방침

- security issue로 분류하지 않는다.
- 신규로 추가되는 HTTP/HTTPS 터널 설정은 `replaceAccessControlAllowOrigin=false`를 기본값으로 둔다.
- 기존 저장된 설정 파일에서 필드가 비어 있으면 load 시 legacy `true` 동작을 유지하고 경고를 남긴다.
- 운영자는 legacy 반사 동작을 계속 유지할지, 명시적으로 `false`로 전환할지 설정 파일에 적어야 한다.
- credential-bearing backend는 allowlist 또는 upstream 고유 정책으로 이행한다.

### mixed-version rollout 및 sunset 정책

- 기본 rollout 모드:
  - 서버 `controlProtocolMode: mixed`
  - 서버 `allowLegacyControlAuth: false`
  - 클라이언트 `allowLegacyFallback: false`
- canary 허용 범위:
  - protocol v2 신뢰 클라이언트가 정상 연결된다.
  - explicit legacy 예외를 켠 경우에만 v1 fallback 또는 shared-key control auth가 동작한다.
  - mixed-version matrix와 rollback rehearsal이 모두 green이어야 한다.
- legacy sunset 기준:
  - Release N: `mixed`를 기본 유지, legacy는 explicit flag로만 허용
  - Release N+1: 신규/교체 클라이언트는 protocol v2만 허용, legacy는 break-glass 용도로만 유지
  - Release N+2: fleet 100% v2, canary green, rollback rehearsal green이 확보되면 legacy control auth 제거를 선언

### canary/rollback 절차

1. 신규 trusted client를 서버에 등록한다.
2. 대상 클라이언트에 `clientId`, `clientSecret`, `ca`, `serverName`을 배포한다.
3. 서버는 `mixed` 모드로 유지한 채 v2 연결 성공과 legacy 거부/허용 정책을 검증한다.
4. 일부 클라이언트에만 canary 적용 후 mixed-version matrix와 회귀 테스트를 재실행한다.
5. 문제가 있으면 서버의 explicit legacy flags 또는 클라이언트의 `allowLegacyFallback`로 한시적 rollback을 수행한다.
6. canary green이 유지되면 `mtls-strict` cutover 후보로 승격한다.
