# Administrator configuration revisions

Persistent configuration writes require the revision of the configuration that
the caller edited. This intentionally rejects older API clients that omit the
revision; update those clients before upgrading the server.

1. Read `GET /api/serverOption` or `GET /api/tunnelingOption` with the existing
   authenticated session. Keep `revisionState.currentRevision` with that response's
   editable data.
2. Send the edited data and `expectedRevision` in the JSON body of the corresponding
   POST or PUT. Tunnel DELETE sends `{ "forwardPort": 9301, "expectedRevision": 2 }`.
3. A successful response supplies `revisionState.currentRevision`. A sequence of
   dependent writes may use the revision returned by its own preceding successful
   write. Stop the sequence if any response has `success: false`.

Missing, nonnumeric, nonpositive, fractional or unsafe-integer revisions receive
HTTP 400. A well-formed but outdated revision receives HTTP 409, including an
otherwise identical write or deletion. Authentication, Origin and CSRF validation
still apply. The revision is request metadata and is not persisted in server or
tunnel options.

On 409, preserve the draft, read the current configuration and reconcile the
changes before explicitly submitting again. Do not stamp an old draft with a
revision obtained by another background read and automatically retry. The admin
editors retain the revision of their own loaded snapshot.

Server and tunnel configuration share one revision and one mutation queue across
administrator listeners. Revision comparison, validation, asynchronous port checks,
runtime application and commit run in that queue. Of two concurrent writes using
the same old revision, at most one configuration change commits.

Login, session, CSRF recovery, certificate endpoints and temporary listener
activation do not acquire this configuration field. Certificate operations are
separate requests and are not made atomic with configuration changes by this
contract. A multi-request operation can partially succeed before a later request
fails; explicitly reload and reconcile that partial result before retrying.
