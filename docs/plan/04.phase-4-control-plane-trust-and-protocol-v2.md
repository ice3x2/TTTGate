# Phase 4: 제어 채널 신뢰와 프로토콜 v2

## 목표

공개 기본 key, 인증서 미검증 TLS, 자기신고 client name, data channel 무바인딩을 제거하고 protocol v2 기반의 신뢰 모델로 이행한다. 이 Phase는 호환성을 깨는 가능성이 크므로 version negotiation과 dual-stack 기간을 전제로 한다.

- [x] 신규 설치 secure-by-default 정책이 정의되었다.

## 상세 구현 지침

### 호환성 전략

- 1차 릴리스:
  - version negotiation 필드 추가
  - v1과 v2 동시 수용
  - server canary 우선
- 2차 릴리스:
  - client 업그레이드 확대
  - v2 비율 모니터링
- 3차 릴리스:
  - insecure legacy shared-key mode 제거

### strict 모드 규칙

- TLS 검증 실패 시 자동 다운그레이드 금지
- 협상 실패 시 자동 legacy fallback 금지
- fallback은 명시적 플래그가 있을 때만 허용

### 인증 모델 원칙

- client identity는 self-declared name이 아니라 검증 가능한 값이어야 한다.
- data channel은 control channel에서 발급된 one-time secret 없이는 attach할 수 없어야 한다.
- handshake 완료 조건에는 proof-of-possession과 서버 측 state/id 검증이 포함되어야 한다.

## 테스트

### Given-When-Then 시나리오

1. 정상 케이스
   - Given v2 서버와 v2 클라이언트가 있다
   - When verified TLS와 capability negotiation을 수행한다
   - Then 연결은 성립하고 authenticated `clientId`가 등록된다
2. 정상 케이스
   - Given v2 서버와 legacy client가 있다
   - When explicit legacy mode가 켜져 있다
   - Then 제한된 호환 모드로만 연결된다
3. 예외 케이스
   - Given 잘못된 CA 또는 위조된 서버 인증서가 있다
   - When 클라이언트가 TLS 연결을 시도한다
   - Then 연결은 거부된다
4. 예외 케이스
   - Given 허가되지 않은 client가 허용된 이름을 사칭한다
   - When control channel 등록을 시도한다
   - Then 인증 실패로 등록이 거부된다
5. 경계값 케이스
   - Given 대량 세션과 높은 handler ID가 존재한다
   - When v2 ID 폭 확장을 사용한다
   - Then packet serialization 오류 없이 세션이 유지된다
6. 예외 케이스
   - Given 재사용된 `AckCtrl` 또는 잘못된 challenge 응답이 있다
   - When 서버가 PoP를 검증한다
   - Then handshake는 완료되지 않고 연결이 거부된다
7. 예외 케이스
   - Given `packet.ID` 또는 handshake state가 기대값과 다르다
   - When 서버가 control packet을 처리한다
   - Then 세션은 종료되고 audit 로그가 남는다
