## Reuse findings and actual state

`HttpHandler.ts:21` owns one `_currentHttpPipe`. Inbound external requests enter it at lines 109-129; `sendData` switches the same parser to response mode at lines 414-436. The end callback at lines 393-405 flips direction/reset and `HttpPipe.reset` at line 134 discards buffered tail. Separating only the parser field is insufficient: origin host/origin URL, active response header/body rewrite state, request method and upgrade context must remain associated with the correct outstanding request. A small per-connection request-context FIFO may be needed; it must not become a general scheduler or invent response reordering.

Context allocation must occur when validated request headers are available, before forwarding those headers upstream; waiting for the request body to finish would lose the association for 100 Continue or an early final rejection. Informational responses retain the current request context; only final-response completion consumes it, with 101 handled as the existing upgrade transition. Continuing request-body parsing and final-response completion have independent lifetimes: preserve the active request's context reference if its response ends before the upload ends.

Reuse search in `src/server/http` and `src/util/ResourcePolicy.ts` found header/body/decompression limits but no pending-request-context count limit. Proposed fixed maximum: 128 outstanding contexts per connection, including the request with an active response. Store only necessary immutable request metadata (method, origin Host, origin header and required upgrade flag), not full headers/body/socket copies. Request header limits already bound field lengths; the context limit bounds aggregate pending metadata. Before forwarding headers for request 129, record a connection-level limit error and terminate that connection through existing ownership cleanup. Do not send an HTTP error that overtakes earlier outstanding responses, forward the overflow request, silently drop it or create a general queue scheduler/user setting. This is a proposed policy for root approval; no limit is implemented by this document.

`HttpPipe.write` at lines 155-256 recursively re-enters while bytes remain, but has no explicit END handling. Completion/reset callbacks can clear the tail or trigger repeated END work. Reuse existing states/callbacks and add an explicit message-boundary progression contract. Never solve this by dropping all bytes after the first message or globally catching and continuing parser errors.

`HttpPipe.readChunkedTrailer` at line 632 consumes terminator/trailers without invoking the raw-data callback. `readChunkedData` also consumes chunk bytes before confirming a split trailing CRLF is available. These share chunk boundary state; #12 requires split-boundary assertions so a terminator fix does not overlook consumed-but-undelivered chunk payload.

`HttpUtil.isTextContentType`, `findHeader(s)`, header setters/removers, and zlib helpers already exist. `uncompressBody` at line 148 and `compressBody` at line 180 select encoding by substring; unsupported/stacked encodings cannot safely pass through a UTF8 string roundtrip. Do not add a second compression library. Existing HttpHandler.rewrite.test.ts is a mocked socket/decompress-limit bypass test; it is a regression to preserve, not evidence of real duplex transport or normal rewriting.

Existing reuse anchors: `test/security/req-05-smuggling.test.ts`, `req-06-crlf-injection.test.ts`, `req-13-chunked-parse.test.ts`; `test/unit/server/http/HttpUtil.branches.test.ts`; `test/component/handler-map-lifecycle-driver.ts` and `socket-owner-terminal.test.ts` for real bound sockets and owned teardown. ## Real network harness and safety contracts

Use a real loopback external TCP client → real accepted SocketHandler wrapped by HttpHandler → real upstream TCP server. Bridge actual HttpHandler Receive data to the upstream socket; upstream data returns through HttpHandler.sendData. A focused harness may explicitly signal upstream FIN, but must be labeled as such: it cannot establish production EOF/drain ordering. Add the actual ExternalPortServerPool closeSession/send-length/output-drain path and a full TTTServer/TunnelClient case for #29, without editing administrator-owned classes. Do not use a test-only direct end_ call to bypass the consumer deadlock under investigation.

Drive requests/responses with raw net sockets so duplicate headers, invalid UTF8, exact chunk framing and deliberate split points survive. Use protocol-observed barriers (upstream received request; client received partial response), not timing sleeps as proof that segments were delivered separately. TCP can coalesce writes; parser unit cases explicitly enumerate splits, while socket cases assert bytes and liveness independently of packet segmentation. Do not use a fake socket sendData accumulator as the sole acceptance test.

Each fixture owns its temporary root/listeners/sockets before any awaited setup, cleans them on setup failure and in finally, and awaits child termination/natural test exit. Deliberately pathological END recursion/17MiB overflow should run in owned bounded children so a baseline hang cannot wedge the whole Jest process. A timeout is failing evidence, not success. Preserve callbacks/owner registry cleanup/output-drain semantics from #26/#27 and cache failure accounting from #19. Check EOF/error visibility and no leaked connection after repeated cycles. No blanket TLS disable; ordinary focused harness is explicit local plaintext HTTP, existing TLS tests remain unchanged.

## Per-issue strict test-first sequence

### #11 — independent directions and message tails

Before production edits reproduce: (1) response Content-Length10 with first five bytes `AAAAA`, then external next request, then last five response bytes; assert client body is exactly ten intended bytes and the second request reaches upstream; (2) second request before any response in a distinct observed write; (3) two requests in one write and two responses in one write; (4) header/body/message-boundary splits. The original issue reports `AAAAAGET /` corruption, loss and destruction; these are targets for fresh RED, not assumed current test results.

Add actual duplex RED for POST headers with Expect:100-continue and a body still withheld: upstream receives headers, sends 100 Continue, client observes it, then sends body; upstream receives exactly that body and returns the final response. Repeat with a partially delivered body and an early final rejection (e.g. 413/417), proving response bytes never enter the upload parser and remaining upload bytes are never emitted as a response. Record the existing close/continue behavior explicitly rather than inventing a retry. A 100 followed by final response for the first request and another final response for the next request must retain FIFO association; interim 1xx does not consume the context. Bound the context queue with real pipelined requests held by an upstream response barrier: 128 contexts are accepted, the 129th headers are not forwarded, the connection closes with a recorded limit error and no out-of-order synthetic HTTP response. Confirm final responses reclaim slots and context/body data is released on connection termination.

Keep request parsing progressing independently of response-body buffering. Preserve tails at end and process them exactly once without recursive END loops. Capture per-request host/origin/method context so a later request cannot rewrite an earlier response using the wrong Host. Verify distinct Host requests, multiple responses including interim status, HEAD no-body context and upgrade tunnel byte pass-through as compatibility controls; do not silently broaden HTTP protocol support or fix unrelated framing policy.

### #12 — complete chunk framing

RED compares delivered bytes, not only an end flag: nonrewritten image/png chunked payload `5\r\nhello\r\n0\r\n\r\n`, optional trailer fields and following message tail. Test split before/after each CR/LF and at the last payload byte; raw forwarding must preserve terminator/trailer bytes exactly once. Pure-body delivery to rewriting must exclude framing while still reaching completion. Retain invalid chunk-size/CRLF security rejections and explicit failure callbacks. Include at least one real HTTP client that completes without waiting for socket close.

### #29 — close-delimited HTTP/1.1 body

RED actual upstream HTTP/1.1 200 + Connection:close + binary body without CL/TE, then FIN; verify complete bytes and client EOF. Include fragmented body, HTTP/1.0 compatibility, empty body and explicit CL0. No-body responses (HEAD context, 1xx, 204, 304) must not wait for EOF or consume next-response bytes; successful CONNECT/101 upgrade behavior must stay distinct. Add explicit parser EOF handling if needed and reject incomplete CL/chunked bodies rather than marking them complete. Check actual pool end/drain boundary before assuming a parser-only fix is enough.

Required separate consumer RED: a close-delimited UTF8 response selected for rewriting contains the internal destination URL and ends via real upstream FIN. Exercise the existing endpoint data/CloseSession path, not only the direct parser harness. Assert rewritten bytes, completed downstream framing and eventual close while the client actually reads; verify no cycle in which output waits for EOF and EOF waits for sendLength/isOutputDrained. Include CloseSession-before-final-data and data-before-CloseSession ordering, fragmented payload and a slow reader. The test must require the rewrite (not accidentally use a binary passthrough control that drains before EOF). If it proves the cycle, seek the exact ownership expansion above before separating input-completion notification from final output-drained closure. Existing raw-socket lengths, final close-once behavior and ownership callbacks remain regression controls.

### #30 — unsupported coding/charset preserves bytes and framing

Assert output body equals original bytes and original Content-Encoding/Content-Length or chunked framing remains coherent. Binary content-type is a control. Select rewriting before headers are emitted: allow only the explicitly supported UTF8/single-encoding path; unsupported cases bypass the transform without decoding. Preserve existing configured unrelated header features and decompression-limit behavior; do not claim arbitrary charset support or silently rewrite a half-decoded stack.

### #32 — immediate bounded rewrite overflow failure

Require prompt visible 502 and orderly connection termination without waiting for the next receive event; test known CL and chunked/unknown-total paths. Preserve separate configured decompression-limit bypass semantics and distinguish encoded input-buffer overflow from decompression expansion. A parser failure return alone is not proof the peer was notified.

## Protocol reference and limits of this proposal

[RFC 9112 §6.3](https://www.rfc-editor.org/rfc/rfc9112.html#section-6.3) specifies body-length precedence and close-delimited responses; [§7.1](https://www.rfc-editor.org/rfc/rfc9112.html#section-7.1) defines chunk terminators/trailers. These support the no-body/EOF controls above, without selecting tunnel wire compatibility policy. Each change must preserve existing anti-smuggling rejections and active socket ownership behavior. This is a proposed bounded scheduling exception, not approval to implement the whole HTTP standard or all unresolved HTTP findings.
