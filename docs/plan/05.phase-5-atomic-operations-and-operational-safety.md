## 상세 구현 지침

### 적용 분류

- hot-apply 가능:
  - response envelope, docs, 일부 상태 노출
- drain 후 재적용:
  - 외부 포트 listener 변경
  - 일부 TLS option 변경
- 재시작 필수:
  - admin bind port/host 변경
  - protocol-wide capability 변경

### 운영 원칙

- 실패 시 현재 listener를 유지한다.
- 부분 실패는 숨기지 않고 API와 로그에 구조화해 노출한다.
- rollout은 포트 단위로 격리한다.

## 테스트

### Given-When-Then 시나리오

1. 정상 케이스
   - Given 사용 가능한 새 포트 설정이 있다
   - When staged apply를 수행한다
   - Then 새 revision이 commit되고 상태 API가 성공을 반환한다
2. 정상 케이스
   - Given 유효한 인증서가 있다
   - When 인증서 교체를 수행한다
   - Then 적용 결과가 상태/문서에 명확히 표시된다
3. 예외 케이스
   - Given 충돌하는 포트 설정이 있다
   - When 설정 변경을 시도한다
   - Then 기존 listener는 살아 있고 새 revision은 commit되지 않는다
4. 예외 케이스
   - Given `-reset false`가 전달된다
   - When CLI를 해석한다
   - Then reset은 실행되지 않는다
5. 경계값 케이스
   - Given 여러 포트 중 하나만 실패하는 변경이 있다
   - When apply를 수행한다
   - Then 응답은 partial 상태를 포함하고 영향 범위가 명시된다

### 테스트 코드 템플릿

```ts
it("should keep the last-known-good listener when staged apply validation fails", async () => {
  const harness = await createApplyHarness();
  const result = await harness.applyInvalidPortChange();

  expect(result.committed).toBe(false);
  expect(result.oldListenerAlive).toBe(true);
});
```
