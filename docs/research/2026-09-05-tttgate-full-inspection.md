## 4. CRITICAL — 제품이 동작하지 않는 결함

### 4.1 관리자 SPA가 부팅되지 않습니다

`admin/src/main.ts:4` 가 `new App({target})` 이라는 Svelte 4 의 클래스 API 를 사용합니다. 그런데 `admin/package.json` 은 Svelte 5 로 올라갔고 실제 설치된 버전은 5.55.5 입니다. Svelte 5 는 컴포넌트를 클래스가 아니라 함수로 컴파일하므로 이 호출은 실패합니다. `admin/svelte.config.js` 에는 하위 호환을 켜는 `compatibility.componentApi` 설정도 없습니다.

감사 과정에서 설치된 컴파일러로 `App.svelte` 를 실제 컴파일해 산출물이 `export default function App($$anchor, $$props)` 형태임을 확인했습니다. 개발 서버에서는 `component_api_invalid_new`, 프로덕션 빌드에서는 `anchor.before is not a function` 이 발생하며 어느 쪽이든 화면에 아무것도 렌더링되지 않습니다.

이 결함은 커밋되지 않은 워킹 트리 변경에서 비롯되었습니다. Svelte 4 에서 5 로 올리는 작업이 의존성 버전만 바꾼 채 중단되었습니다.

**권고**: `mount(App, {target})` 으로 교체하십시오.

### 4.2 인증서 입력 컴포넌트가 무한 갱신 루프에 빠집니다

`admin/src/layout/InputCertFile.svelte:69` 의 `afterUpdate` 콜백이 `bind:this` 로 묶인 세 개의 참조를 매번 다시 씁니다. Svelte 5 의 레거시 `afterUpdate` 는 콜백 실행 전에 컴포넌트의 모든 반응형 소스를 읽으므로, 자신이 읽는 상태를 스스로 다시 쓰는 구조가 되어 `effect_update_depth_exceeded` 로 종료됩니다. Svelte 4 는 `afterUpdate` 를 flush 당 한 번으로 중복 제거했기 때문에 이 문제가 드러나지 않았습니다.

같은 파일 5행의 `beforeUpdate` 는 임포트만 되어 있고 사용되지 않습니다. `Gauge.svelte` 와 `Timer.svelte` 도 같은 레거시 생명주기 API 를 사용합니다.

### 4.3 관리자 UI에서 모든 설정 변경이 403으로 거부됩니다

백엔드는 세션 쿠키가 있는 상태 변경 요청에 대해 `X-CSRF-Token` 헤더와 `csrfToken` 쿠키의 double-submit 일치를 의무화합니다 (`src/server/admin/AdminServer.ts:1329-1340`). 그런데 `admin/src` 전체에서 `csrf` 라는 문자열이 **한 건도 검색되지 않습니다.**

프론트엔드의 상태 변경 호출 일곱 곳은 모두 `credentials: "same-origin"` 으로 쿠키만 보내고 헤더는 싣지 않습니다.

| `admin/src/controller/ServerOptionCtrl.ts` | 133 | 서버 옵션 저장 |

서버는 이미 `/api/csrfToken` 엔드포인트를 제공하고 로그인 응답에서 `csrfToken` 쿠키를 `HttpOnly` 없이 발급합니다. 프론트엔드가 이 값을 읽어 헤더로 실어 보내기만 하면 됩니다. 백엔드 보안 강화 라운드가 프론트엔드에 반영되지 않아 생긴 계약 파손입니다.

덧붙여 프론트엔드는 401 만 세션 만료로 처리하므로, 403 응답은 사용자에게 원인 불명의 실패로 보입니다.

### 4.4 신규 설치에서 최초 비밀번호를 설정할 수 없습니다

서버는 저장된 키가 비어 있을 때 요청 본문의 `bootstrapToken` 을 검증하고, 없으면 403 과 `bootstrapRequired` 를 반환합니다. 그런데 `admin/src/controller/LoginCtrl.ts:36` 은 `{key: hash}` 만 전송하며 부트스트랩 토큰을 입력받는 화면 자체가 없습니다. 사용자에게는 "The password is incorrect." 만 표시됩니다.

`README.md` 는 `config/.bootstrap-token` 을 읽어 최초 비밀번호를 설정하라고 안내하지만, 그 값을 넣을 곳이 UI에 존재하지 않습니다.

### 4.5 제어 패킷 하나로 서버·클라이언트 프로세스가 종료됩니다

`src/commons/CtrlPacket.ts:80-85` 의 `waitReceiveLength` 게터가 길이 검사 없이 `this._data.readUInt32BE(0)` 을 호출합니다. `fromBuffer` 는 `dataLength == 0` 을 `SyncCtrl` 에 대해서만 거부하므로, 페이로드가 빈 `CloseSession` 패킷은 정상으로 파싱됩니다.

호출부인 `src/server/TunnelServer.ts:594-596` 의 반복문은 `try` 블록 **바깥**에 있고, 저장소 전체에 `process.on('uncaughtException')` 등록이 한 건도 없습니다.

빈 버퍼에 `readUInt32BE(0)` 을 호출하면 `ERR_BUFFER_OUT_OF_BOUNDS` 가 발생하는 것을 실측으로 확인했습니다. 서버 측은 인증된 제어 채널에서 도달 가능하고, 클라이언트 측(`src/client/TunnelClient.ts:349`)은 서버가 보낸 프레임만으로 도달합니다.

### 4.6 비활성 외부 포트에 접속 한 번이면 서버가 죽습니다

`src/server/ExternalPortServerPool.ts:335-338` 은 비활성 포트의 연결을 거절할 때 `handler.end_()` 만 호출하고 반환합니다. 그런데 `OPTION_BUNDLE_KEY` 번들은 그 아래 343행에서야 설정됩니다. 소켓이 End 상태가 되면 `:283` 이 `handler.getBundle(OPTION_BUNDLE_KEY).forwardPort` 를 읽으면서 `TypeError` 를 던집니다.

`inactiveOnStartup` 으로 기동한 포트나 `active(port, timeout)` 의 타이머가 만료된 포트가 대상입니다. 감사 과정에서 비활성 포트에 1회 접속해 실제로 uncaught TypeError 를 재현했습니다. 전역 예외 처리기가 없으므로 서버 프로세스 전체가 죽고 모든 터널이 동시에 끊깁니다.

### 4.7 클라이언트 제어 채널에 프레이밍 예외를 흡수하는 코드가 없습니다

서버 측 `src/server/TunnelServer.ts:576-593` 은 `readCtrlPacketList` 를 `try`/`catch` 로 감싸지만, 클라이언트 측 `src/client/TunnelClient.ts:292` 에는 그 보호가 없습니다. 잘못된 prefix, 잘못된 command 값, 상한 초과 길이 중 하나만 발생해도 클라이언트 프로세스가 종료됩니다. 같은 프레이밍 코드를 공유하면서 오류 처리 수준만 비대칭입니다.

### 4.8 메타 역직렬화 예외를 흡수하는 호출부가 한 곳도 없습니다

`src/commons/CtrlMetaGuards.ts:8` 의 주석은 "가드 실패는 Error throw. 호출부에서 try/catch로 흡수하여 패킷 폐기" 라고 계약을 명시합니다. 그러나 실제 호출부 다섯 곳 어디에도 `try`/`catch` 가 없습니다. 문서화된 계약과 구현이 어긋나 있으며, 결과는 4.5와 같은 프로세스 종료입니다.

### 4.9 요청과 응답이 하나의 HTTP 파서를 공유해 서로를 오염시킵니다

`src/server/http/HttpHandler.ts:21` 은 `HttpPipe` 인스턴스를 **하나만** 두고 요청과 응답 양방향에 함께 사용합니다.

감사 과정에서 실제 인스턴스를 구동해 확인한 결과는 다음과 같습니다. 응답 본문이 절반만 도착한 상태에서 클라이언트가 다음 요청을 보내면, 그 요청 바이트가 응답 본문으로 편입되어 클라이언트에게 되돌아갑니다. `Content-Length: 10` 응답의 본문이 `AAAAAGET /` 로 관측되었고, 두 번째 요청은 내부망으로 전달되지 않았습니다.

keep-alive 파이프라이닝을 쓰는 모든 클라이언트에서 응답 오염과 요청 유실이 발생합니다.

### 4.10 chunked 응답의 종료 시퀀스가 완결되지 않습니다

`src/server/http/HttpPipe.ts:638-649` 의 `readChunkedTrailer` 는 종료 CRLF 를 소비만 하고 `onDataCallback` 을 호출하지 않습니다. 그래서 클라이언트는 `0\r\n` 까지만 받고 마지막 `\r\n` 을 받지 못합니다.

본문 재작성을 타지 않는 모든 chunked 응답, 즉 이미지를 비롯한 바이너리 응답 전부가 미완결 상태로 남아 클라이언트가 타임아웃까지 대기합니다.

### 4.11 로그인 무차별 대입 차단이 무력화되어 있습니다

`src/server/admin/AdminServer.ts:1203-1212` 의 레이트리밋 버킷 키가 **제출된 비밀번호의 SHA-256 앞 16자** 를 포함합니다. 매번 다른 비밀번호를 넣으면 시도마다 새 버킷이 생성되어 실패 카운터가 항상 1에 머물고, 5회 임계값에 영원히 도달하지 않습니다.

비밀번호 하나로 인증하는 체계에는 계정 축이 존재하지 않으므로, 키에서 비밀번호 파생값을 제거하고 네트워크 버킷만으로 집계해야 합니다.

문제는 기존 테스트가 이 동작을 **정상으로 고정하고 있다**는 점입니다. `test/unit/server/admin/req-07-rate-limit.test.ts:68-69` 가 "다른 잘못된 비밀번호는 401" 을 단언합니다.

### 4.12 CI가 코드 변경에 대해 테스트를 한 건도 실행하지 않습니다

저장소 전체에서 Jest 를 실행하는 유일한 지점은 `.github/workflows/supply-chain-audit.yml:103` 의 `npx jest test/supply-chain/` 입니다. 대상이 공급망 디렉터리로 한정되어 나머지 59개 스위트는 어떤 경로로도 실행되지 않습니다.

이 워크플로우는 main 브랜치 푸시와 매주 월요일 스케줄에서도 기동하지만, 실행하는 테스트는 여전히 공급망 6개뿐입니다. PR 트리거에는 추가로 경로 필터가 걸려 있어 대상이 다음 다섯 개로 한정됩니다.

```
package.json
package-lock.json
admin/package.json
admin/package-lock.json
.github/workflows/supply-chain-audit.yml
```

`src/` 만 수정한 PR 은 이 워크플로우를 기동시키지도 않습니다. 나머지 두 워크플로우(`build-release.yml`, `build-release-binaries.yml`)는 `npm run dist` 만 실행하며 테스트 단계가 없습니다.

결과적으로 6개 Phase 에 걸쳐 축적한 65개 스위트 중 **59개가 자동 실행 지점을 갖지 못합니다.** 보안 회귀 테스트가 회귀를 막지 못하는 상태입니다.

### 4.13 CI가 실행하는 그 유일한 테스트가 네트워크 실패 시 무조건 통과합니다

`test/supply-chain/r3-req-04-medium-cleared.test.ts:23` 의 `runAudit` 는 `npm audit` 이 실패하면 문자열 `"{}"` 를 반환합니다. 그러면 `vulnerabilities` 가 빈 객체가 되어 `expect(hits).toEqual([])` 가 취약점 0건으로 통과합니다.

`test/supply-chain/r3-req-02-crypto-js-removed.test.ts:51` 은 `npm ls` 출력이 비면 `expect(true).toBe(true)` 로 빠져나갑니다.

오프라인, 레지스트리 장애, 프록시 차단 환경에서 공급망 게이트가 조용히 녹색이 됩니다.

### 4.14 Sentinel이 자기 프로세스 대신 PID 1에 SIGTERM을 보냅니다

`src/Sentinel.ts:234` 가 `process.kill(1)` 을 호출합니다. `process.kill` 의 첫 인자는 대상 PID 이고 기본 시그널은 SIGTERM 이므로, 이 호출은 **PID 1** 에 시그널을 보냅니다. 컨테이너에서는 컨테이너 주 프로세스가, 호스트에서 root 로 구동하면 init 이 대상입니다.

바로 윗줄 231행이 자신에게 SIGTERM 을 보내지만 Node 는 시그널을 비동기로 처리하므로 현재 동기 실행은 끝까지 진행되어 234행이 반드시 실행됩니다.

진입 경로는 감시 대상 조회 실패입니다. 3초마다 반복되므로 일시적 자원 부족 한 번이면 도달합니다. 작성 의도는 `process.exit(1)` 이었던 것으로 보입니다.

### 4.15 공급망에서 제거한 crypto-js가 배포본에서 되살아납니다

`package-build.json` 의 17행과 23행에 `@types/crypto-js` 와 `crypto-js` 가 그대로 남아 있습니다. `deploy.js:26` 은 이 파일을 `dist.js/package.json` 으로 복사하므로, 배포본에서 의존성을 설치하면 crypto-js 가 다시 들어옵니다.

검증 테스트 `test/supply-chain/r3-req-02-crypto-js-removed.test.ts:15` 는 루트 `package.json` 만 읽기 때문에 이 잔존을 잡지 못하고 통과합니다. 직전 커밋 `b07518b` 이 수행한 crypto-js 제거 작업이 배포 경로에서는 완결되지 않았습니다.

## 5. HIGH — 정상 사용 중 데이터가 유실되거나 자원이 고갈되는 결함

### 5.1 유휴 터널이 60초마다 끊깁니다

`src/server/TunnelServer.ts:66` 의 `DEFAULT_SESSION_TTL_MS` 가 60초이고, 세션 활동 시각을 갱신하는 지점은 `:312`, `:333`, `:546` 세 곳뿐입니다. 모두 데이터 송수신과 세션 개시입니다. TCP keepalive 프로브는 애플리케이션 데이터가 아니므로 활동으로 집계되지 않습니다.

`configureSessionTtl` 은 최소 1초에서 최대 1시간만 허용해 비활성화가 불가능하고, 실제 코드에서는 테스트만 이 함수를 호출하므로 운영 환경은 항상 60초로 동작합니다.

유휴 SSH 세션, RDP, 데이터베이스 커넥션 풀처럼 조용한 시간이 긴 TCP 터널이 1분마다 끊깁니다. 터널링 도구의 핵심 용도가 깨지는 결함입니다.

주목할 점은 E2E 테스트 `test/e2e/req-09-pool-swap-zombie.test.ts:101` 이 TTL 을 1초로 낮춰 이 동작을 정상으로 단언한다는 것입니다. 테스트가 결함을 고정하고 있습니다.

### 5.2 파일 캐시 읽기 실패 시 데이터가 조용히 사라집니다

`src/util/SocketHandler.ts:706` 이 캐시 읽기 결과가 없으면 빈 버퍼로 대체합니다. 그런데 뒤이은 전송 루프는 원래 길이로 0바이트 검사를 통과시키고, 쓰기 성공 후 송신 누적량에 원래 길이를 더합니다. 0바이트를 보내고 성공으로 보고하는 것입니다.

임의의 TCP 트래픽을 중계하는 제품에서 데이터가 오류 기록도 없이 사라지고, 수신 측 스트림은 잘린 채로 이어집니다. 파일 전송이 손상되며 원인 추적이 불가능합니다.

`src/util/FileCache.ts:116-120` 의 블록 재사용 분기가 길이만 갱신하고 기존 식별자를 그대로 유지합니다. 식별자 증가는 신규 블록 분기에서만 일어납니다. 따라서 해제된 식별자가 다음 쓰기에서 다른 데이터에 다시 붙습니다.

### 5.4 로그 파일이 영구히 삭제되지 않습니다

`src/util/logger/LogWriter.ts:92` 와 `:112` 의 정규식이 템플릿 리터럴 안에 작성되어 있습니다. 템플릿 리터럴에서 숫자 클래스 이스케이프는 인식되지 않아 문자 d 로 축약됩니다. 결과 패턴은 다음과 같습니다.

```
^server-d{4}.d{2}.d{2}.log$
```

이 패턴은 실제 로그 파일명과 일치하지 않습니다. 따라서 로그 파일 목록이 항상 비어 반환되고 오래된 파일 정리가 어떤 파일도 삭제하지 못합니다. 부팅 시 지정한 2일 보관 정책과 기본값 30일이 모두 무효입니다.

터널링 서버는 연결마다 로그를 남기므로 로그 디렉터리가 빠르게 증가해 결국 디스크를 소진합니다.

### 5.5 소켓 계층 로그가 운영 환경에서 전부 소실됩니다

`SocketHandler` 와 `TCPServer` 만 빈 이름으로 로거를 요청합니다. 빈 이름은 파일 출력이 꺼진 기본 writer 로 연결됩니다. 그런데 데몬 모드는 자식 프로세스의 표준 출력과 표준 오류를 모두 버리므로 콘솔 출력마저 사라집니다.

파일 캐시 쿼터 초과 경고, 소켓 쓰기 오류, 타임아웃 기록이 운영 환경에서 하나도 남지 않습니다. 5.2의 데이터 유실이 발생해도 흔적이 없는 이유가 여기 있습니다.

### 5.6 클라이언트가 끊어진 터널을 감지하지 못합니다

`src/client/ClientApp.ts:122` 의 keepAlive 기본값이 0 이고, TLS 옵션 생성기는 이 값이 0 이면 소켓 keepalive 를 끕니다. 제어 연결에는 주기적 트래픽도 없고 Ping 패킷도 프로토콜에 정의되어 있지 않습니다.

NAT 유휴 타임아웃, 케이블 분리, 서버 호스트 전원 차단처럼 종료 신호가 오지 않는 단절에서 클라이언트는 끊긴 터널을 무한정 정상으로 인식하고 재연결하지 않습니다. 서버는 자체 기본값 10초 keepalive 로 단절을 감지하므로, 터널은 프로세스를 수동 재시작할 때까지 죽어 있습니다.

한편 연결 옵션 생성부는 keepalive 를 설정하지 않아 데이터 핸들러만 기본값 60초를 받습니다. 생존 감지가 가장 중요한 제어 연결이 유일하게 keepalive 없이 동작하는 역전 구조입니다.

### 5.7 클라이언트 데이터 핸들러의 종료 이벤트가 처리되지 않습니다

`src/client/TunnelClient.ts:388-420` 의 콜백에 연결과 수신 분기만 있고 종료 분기가 없습니다. 제어 연결은 살아 있는데 데이터 연결 하나만 끊기면 세션이 활성 맵에 영구히 남습니다.

이후 송신은 죽은 핸들러에 쓰기를 시도하고 조용히 버려집니다. 내부망 엔드포인트 소켓은 닫히지 않고, 서버에도 종료가 통보되지 않습니다. 제어 연결이 죽을 때까지 세션과 내부망 커넥션이 누적됩니다.

### 5.8 폐기된 클라이언트의 지연 콜백이 새 연결을 무너뜨립니다

`src/client/TTTClient.ts:48` 의 상태 변경 콜백이 어느 클라이언트가 보낸 것인지 확인하지 않습니다. 핸드셰이크 실패로 폐기된 이전 클라이언트의 소켓이 5초 뒤에 종료 이벤트를 발화하면, 이미 새로 만들어진 연결이 살아 있는데도 온라인 상태가 뒤집히고 사용 중인 엔드포인트 풀이 폐기됩니다.

그 결과 클라이언트는 서버에 온라인으로 보이지만 어떤 세션도 열 수 없는 상태가 됩니다. 이어서 중복 재연결 타이머가 등록되어 서버가 동일 이름의 클라이언트를 둘 보게 됩니다.

### 5.9 클라이언트 재연결 때마다 서버에 핸들러가 누적됩니다

`src/server/ClientHandlerPool.ts:545-551` 이 종료 시 소켓 이벤트 콜백을 빈 함수로 교체합니다. 그런데 `src/util/TCPServer.ts:118-123` 의 핸들러 맵 정리는 바로 그 콜백 안에만 존재합니다. 소켓 자체는 닫히지만 핸들러 객체가 서버 수명 내내 참조로 남습니다.

감사 과정에서 제어 연결 하나와 데이터 핸들러 하나를 붙인 뒤 제어를 끊었더니, 데이터 소켓이 파괴된 상태인데도 맵에 항목이 남는 것을 확인했습니다.

### 5.10 HTTP 외부 포트는 접속 하나마다 핸들러를 영구 누적합니다

`HttpHandler` 생성자가 소켓 이벤트 콜백을 가로채면서 같은 문제가 발생합니다. 감사 과정에서 HTTP 포트에 10회 접속 후 종료했더니 맵에 10개가 남았고, 같은 시나리오를 TCP 포트로 하면 살아 있는 소켓 수와 정확히 일치했습니다.

웹 트래픽을 중계하는 포트에서 커넥션 수만큼 메모리가 증가합니다.

### 5.11 4GiB를 넘긴 세션은 종료 패킷조차 만들지 못합니다

`src/commons/CtrlPacket.ts:140-141` 이 누적 수신량을 32비트로 기록하는데, 그 값의 출처인 `src/util/SocketHandler.ts:364` 의 카운터는 어디에서도 초기화되지 않습니다. 한 세션으로 4GiB 를 초과 전송한 뒤 닫으면 범위 초과 예외가 발생하며, 호출부에 예외 처리가 없어 그대로 전파됩니다.

대용량 파일 전송이라는 정상 사용에서 도달하는 경로입니다.

### 5.12 연결 종료로 길이를 구분하는 HTTP 응답의 본문이 전량 유실됩니다

`src/server/http/HttpPipe.ts:190-198` 은 길이 정보가 없는 응답에 대해 HTTP/1.0 만 본문 있음으로 처리하고, HTTP/1.1 은 즉시 종료 처리합니다. 표준이 허용하는 연결 종료 구분 응답에서 클라이언트가 빈 본문을 받습니다.

감사 과정에서 실제 파서 인스턴스를 구동해 확인한 결과, `HTTP/1.1 200 OK` 와 `Connection: close` 와 본문 조합에서 전달 바이트가 0 이고 본문이 잔여 버퍼에 남은 채 폐기되었습니다.

### 5.13 본문 재작성이 바이너리와 비 UTF-8 응답을 파괴합니다

`src/server/http/HttpHandler.ts:482-489` 가 본문을 문자열로 바꾼 뒤 다시 버퍼로 되돌립니다. 감사 과정에서 확인한 실제 손상 사례는 다음과 같습니다.

| 입력 | 결과 |
|---|---|
| zstd 로 압축된 본문 | 복구 불가능하게 훼손 |
| EUC-KR 문자셋 본문 | 모든 바이트가 대체 문자로 치환 |
| brotli 와 gzip 이중 압축 | gzip 만 풀고 brotli 계층 훼손 |

한국어 EUC-KR 페이지를 서비스하는 내부망 웹서버가 정확히 이 경로에 해당합니다.

### 5.14 Host 치환이 무관한 헤더를 훼손합니다

`src/server/http/HttpHandler.ts:352-357` 이 모든 헤더 값에 대해 호스트 문자열을 부분 문자열로 치환합니다. 감사 과정에서 확인한 사례는 다음과 같습니다.

| 원본 헤더 | 치환 후 |
|---|---|
| `User-Agent: Mozilla/5.0` | `Mozillinternal.example/5.0` |
| `Cookie: sid=aaa` | `sid=internal.exampleaa` |

짧은 호스트명이나 IP 주소를 쓰는 배포에서 인증 헤더와 쿠키가 손상됩니다.

### 5.15 재작성 상한을 넘는 텍스트 응답이 통지 없이 사라집니다

`src/server/http/HttpHandler.ts:366-389` 가 상한 초과 시 실패를 반환하지만 소켓 파괴는 다음 수신이 있어야 일어납니다. 감사 과정에서 17MiB 텍스트 응답을 보냈더니 클라이언트가 받은 바이트는 헤더 73바이트뿐이었고 소켓은 살아 있었습니다. 클라이언트가 무한 대기합니다.

### 5.16 중복 Host 헤더가 검증 없이 내부망으로 전달됩니다

두 개의 Host 헤더를 함께 보내면 첫 번째만 치환되고 두 번째는 원문 그대로 내부망에 도달합니다. 내부 서버가 어느 값을 채택하느냐에 따라 가상 호스트 라우팅과 캐시 키가 갈립니다. 감사 과정에서 두 개의 Host 헤더를 함께 보내 두 번째가 원문 그대로 전달되는 것을 확인했습니다. 기존 밀반입 테스트는 Content-Length 와 Transfer-Encoding 중복만 검증합니다.

### 5.17 관리자 설정 저장에 낙관적 잠금이 없습니다

리비전 값이 응답에만 실리고 요청에서는 검증되지 않습니다. 두 관리자가 같은 스냅샷에서 서로 다른 필드를 저장하면 나중 요청이 앞선 변경을 덮어쓰면서도 양쪽 모두 성공을 반환합니다. 본문 파싱, 포트 검사, 런타임 적용에 비동기 대기 지점이 있어 두 요청이 실제로 교차 실행됩니다.

### 5.18 커밋 실패 시 런타임 롤백이 없습니다

디스크 소진이나 권한 오류 상태에서 서버 옵션을 저장하면 원자적 쓰기 예외가 그대로 올라가 일반 500 응답이 됩니다. 실패 경로가 `recordRollback` 을 호출하지만, `src/server/ServerOptionStore.ts:114-123` 의 이 함수는 롤백 사실을 메타데이터로 기록할 뿐 메모리와 런타임 상태를 복원하지 않습니다. 결과적으로 메모리와 디스크와 런타임 세 상태가 어긋난 채 남습니다.

### 5.19 인증서 파일명이 검증 없이 경로로 사용됩니다

`src/server/CertificationStore.ts:180`, `:183`, `:186` 이 사용자 입력 이름을 그대로 경로에 결합합니다. 검증은 PEM 값만 확인하고 이름은 보지 않습니다. 인증된 관리자가 이름에 상위 경로 참조를 넣으면 프로세스 권한으로 임의 경로에 기록할 수 있고, 다음 갱신 시 그 경로가 삭제됩니다. 비밀번호 해시 파일을 덮어쓰면 영구 로그인 불가 상태가 됩니다.

### 5.20 터널링 옵션 hot apply에 정규화되지 않은 값이 전달됩니다

`src/server/admin/AdminServer.ts:545` 는 정규화한 복사본을 응답에 담지만, `:560` 의 런타임 적용에는 정규화되지 않은 원본을 넘깁니다. TLS 필드를 생략해 https 터널을 저장하면 저장본에는 TLS 사용으로 기록되는데 실제 리스너는 평문으로 열립니다. 재기동하면 TLS 로 바뀌므로 재기동 전후 동작이 달라집니다.

### 5.21 매칭되지 않는 POST와 DELETE 요청에 아무 응답도 반환하지 않습니다

`src/server/admin/AdminServer.ts:167-178` 의 메서드별 라우팅에 404 폴백이 GET 경로에만 있습니다. 존재하지 않는 POST 경로를 호출하면 응답이 오지 않고 소켓이 타임아웃까지 점유됩니다. 감사 과정에서 동일 구조의 재현 서버로 10초 뒤 연결 초기화를 확인했습니다.

### 5.22 TCPServer 재시작 시 오류 핸들러가 재부착되지 않습니다

`src/util/TCPServer.ts:160-164` 의 시작 함수가 새 서버 객체를 만들지만 생성자에서 등록한 오류와 종료와 리스닝 핸들러는 이전 객체에만 남습니다. 리스너 없는 오류 이벤트는 Node 가 예외로 던지므로 포트 충돌 한 번에 프로세스가 죽습니다.

### 5.23 백프레셔를 완전히 끌 수 있는 설정 구멍이 있습니다

서버 버퍼 한도 검증이 값이 없을 때만 기본값을 채우고 하한을 확인하지 않습니다. 0 이 그대로 통과해 내부적으로 무제한으로 변환되면 백프레셔 판정이 항상 거짓이 되어 읽기가 한 번도 멈추지 않습니다. 느린 수신자 하나가 전역 메모리 예산을 단독으로 소진합니다.

### 5.24 v1 클라이언트가 붙은 서버는 세션 55535개 이후 전면 실패합니다

핸들러 식별자 카운터가 10000에서 시작해 단조 증가하며 순환이 없는데, 전송 시 16비트로 절단됩니다. legacy 모드를 허용한 서버에 메타를 해석하지 않는 v1 클라이언트가 붙고 누적 세션 수가 55535를 넘으면, 절단된 식별자 때문에 모든 신규 세션이 열리지 않습니다. 서버 재시작 전까지 복구되지 않습니다.

### 5.25 상태 패킷 뒤에 이어진 바이트가 영원히 읽히지 않습니다

`src/server/TunnelServer.ts:509` 가 잔여 버퍼를 저장하지만, 유일한 읽기 지점인 `:501` 은 그보다 앞선 조건 안에 있고 507행이 상태를 이미 바꿉니다. 상태 패킷과 첫 터널 페이로드가 한 청크로 도착하면 페이로드 선두가 조용히 유실됩니다. HTTP 터널이라면 요청 라인 일부가 사라집니다.

### 5.26 상태 패킷의 경계 판정이 모호합니다

길이 필드도 토큰 유무 플래그도 없이 버퍼 길이만으로 판정합니다. TCP 가 특정 경계에서 분할하면 토큰이 없는 것으로 오판해 세션이 종료되고, 반대로 뒤따르는 페이로드가 합쳐지면 페이로드 앞 두 바이트를 토큰 길이로 오독합니다. 감사 과정에서 HTTP 요청 선두가 18245바이트 토큰으로 해석되는 사례를 확인했습니다.

### 5.27 배포 파이프라인에 타입 검사와 테스트 게이트가 없습니다

`deploy.js` 는 Vite 빌드와 TypeScript 컴파일만 수행합니다. Vite 빌드는 타입 검사를 하지 않고 `svelte-check` 는 파이프라인에서 호출되지 않으므로, 4장의 프론트엔드 CRITICAL 네 건이 모두 빌드를 통과해 그대로 패키징됩니다. `npm ci` 단계도 없어 잠금 파일이 실제 설치에 반영되지 않습니다.

### 7.5 테스트 자체의 결함

**결함을 정상으로 고정한 테스트.** `test/unit/server/admin/req-07-rate-limit.test.ts:68-69` 가 4.11의 레이트리밋 무력화를 정상 동작으로 단언합니다. `test/e2e/req-09-pool-swap-zombie.test.ts:101` 이 5.1의 60초 TTL 을 정상 동작으로 단언합니다. 이 두 테스트는 수정과 함께 개정해야 합니다.

**실패를 재시도로 덮는 헬퍼.** `test/helpers/tunnelHarness.ts:170-179` 의 왕복 함수는 페이로드 불일치 시 예외를 던지고, 상위의 대기 함수가 10초 동안 50밀리초 간격으로 전체 왕복을 재시도합니다. `test/e2e/req-09-pool-swap-zombie.test.ts:88-97` 은 이 헬퍼로 "초기 바이트 손실 0" 을 주장하지만, 첫 시도에서 바이트가 유실되어도 재시도가 성공하면 통과합니다.

**정상 경로를 검증하지 않는 테스트.** `test/unit/server/http/HttpHandler.rewrite.test.ts:135` 는 본문 호스트 치환의 우회 조건만 확인하고, 정상 조건에서 실제로 치환이 일어나는지 단언하지 않습니다. 기능이 망가져도 통과합니다.

**위양성 통과 가능성.** `test/component/client/TlsVerification.test.ts:79` 의 거부 테스트는 연결 성립 부재를 단언하지 않아, 신뢰되지 않은 인증서로 연결이 성립한 뒤 닫혀도 통과합니다.

**커버리지 실행에서 자동 비활성화되는 테스트.** 상수시간 비교 마이크로벤치 두 건이 커버리지 계측 중에는 건너뜁니다. 계측 오버헤드 때문에 불가피하지만, 그 결과 커버리지 경로에서 타이밍 부채널 회귀 신호가 사라집니다.

**NO-MOCK 정책과 실제의 불일치.** `jest.config.ts:4` 가 실환경 테스트만 허용한다고 선언하지만, `test/unit/server/TunnelServer.keepalive.test.ts:10` 은 TCP 서버 생성을 빈 객체로 대체합니다. keepAlive 가 실제 리스너에 반영되는지가 아니라 인자 전달 여부만 확인됩니다.

**누수를 경고로 강등하는 실행 옵션.** `package.json` 의 테스트 스크립트가 `--forceExit` 를 사용합니다. 프로세스가 종료되지 않는다는 가장 강한 자원 누수 신호가 차단됩니다. 5.9와 5.10의 핸들러 누수가 이 옵션 뒤에 가려져 있을 가능성이 있습니다.

**부하에 따른 불안정성.** 감사 서브에이전트 8개가 동시에 도는 상태에서 커버리지 실행을 시도했을 때 3개 스위트가 실패했고, 부하가 없는 상태로 재실행하니 65개 전부 통과했습니다. 실패한 것 중 확인된 하나는 `test/unit/tools/lint-auth-compare.test.ts` 로, 자식 프로세스 생성이 비정상 종료 코드를 반환했습니다. CI 러너처럼 자원이 빠듯한 환경에서 간헐적 실패가 발생할 수 있습니다.

**요구사항 추적 단절.** `docs/plan/srs/` 의 366개 요구사항 문서에 테스트 파일 참조가 0건입니다. 테스트 쪽 REQ 번호 체계와 SRS 번호 체계가 서로 연결되지 않아, 366개 요구사항 중 무엇이 테스트로 보장되는지 확인할 방법이 없습니다.

**관리자 UI 테스트 전무.** `admin/` 하위에 테스트 파일도, 테스트 러너 설정도, 테스트 스크립트도 없습니다. Svelte 4에서 5로의 메이저 업그레이드와 crypto-js 제거라는 파괴적 변경이 동시에 이루어졌는데 회귀를 잡을 자동 검증 수단이 하나도 없습니다. 4장의 프론트엔드 CRITICAL 네 건이 모두 발견되지 않은 채 남아 있었다는 사실이 이 위험을 실증합니다.

**작업 트리 오염.** `test/.tmp-req04-lint/auth-compare.json` 이 미추적 상태로 저장소에 남아 있습니다. 테스트가 산출물을 작업 트리에 씁니다.

### 7.6 종합 판단

테스트는 **양적으로는 충분해 보이지만 방향이 한쪽으로 치우쳐 있습니다.**

지난 6개 Phase 는 보안 취약점을 하나씩 잡으면서 그때마다 회귀 테스트를 남겼습니다. 그 결과 65개 파일 중 34개가 REQ 번호를 달고 있으며, 이들은 "이미 고친 것이 다시 깨지지 않는가" 를 잘 지킵니다.

문제는 세 가지입니다.

첫째, **아직 고치지 않은 것을 찾는 테스트가 없습니다.** 기능 정상 동작을 검증하는 테스트가 빈약해, 이번 감사에서 발견한 CRITICAL 15건 중 단 한 건도 기존 테스트가 잡지 못했습니다.

둘째, **그 테스트들이 CI에서 실행되지 않습니다.** 회귀 방지 장치를 만들어 두고 작동시키지 않은 상태입니다.

셋째, **일부 테스트가 결함을 정상으로 고정했습니다.** 레이트리밋 무력화와 60초 TTL 이 그렇습니다. 이 경우 테스트는 보호 장치가 아니라 수정을 가로막는 장애물이 됩니다.

## 8. 왜 빌드와 테스트가 녹색인데 제품이 동작하지 않는가

이 질문에 대한 답이 이번 검사의 핵심입니다.

**계층 사이의 계약이 검증되지 않습니다.** 백엔드는 CSRF 헤더를 요구하도록 바뀌었고 그 동작을 검증하는 테스트도 있습니다. 프론트엔드는 헤더를 보내지 않습니다. 두 사실 모두 각자의 영역에서는 문제가 없지만, 조립하면 제품이 동작하지 않습니다. 이 조합을 검증하는 지점이 어디에도 없습니다.

**빌드가 타입 검사를 건너뜁니다.** Vite 빌드는 타입을 확인하지 않고, `svelte-check` 는 배포 파이프라인에서 호출되지 않습니다. Svelte 4의 클래스 API 호출이 Svelte 5 환경에서 빌드를 통과합니다.

**배포 매니페스트가 검증 대상이 아닙니다.** 공급망 테스트가 루트 `package.json` 만 읽어서, 배포본에 crypto-js 가 남아 있는데도 통과합니다.

**테스트가 실행되지 않습니다.** 앞의 세 가지를 다 잡았더라도, `src` 만 수정한 변경에 대해 CI 가 테스트를 한 건도 돌리지 않으므로 발견 시점이 배포 이후로 미뤄집니다.

## 9. 권고 조치

### 9.1 즉시 (제품을 동작 상태로 되돌리기)

1. `admin/src/main.ts` 를 `mount(App, {target})` 으로 교체합니다.
2. `admin/src/layout/InputCertFile.svelte` 의 `afterUpdate` 를 제거하고 prop 변화 기반으로 재작성합니다. `Gauge.svelte` 와 `Timer.svelte` 의 레거시 생명주기도 함께 정리합니다.
3. 공통 fetch 래퍼를 만들어 모든 상태 변경 요청에 CSRF 헤더를 싣습니다. 상태 코드 판정과 JSON 파싱 오류 처리도 이 래퍼로 일원화합니다.
4. `package-build.json` 에서 crypto-js 두 항목을 제거하고, 공급망 테스트의 검사 대상에 이 파일을 추가합니다.
5. `/api/emptyKey` 라우팅을 복원하거나, 부트스트랩 응답 플래그로 최초 설정 여부를 판단하도록 계약을 정리합니다. 부트스트랩 토큰 입력 화면을 추가합니다.

### 9.2 즉시 (원격 종료 경로 차단)

1. `waitReceiveLength` 게터에 길이 검사를 추가하고, 명령별 최소 페이로드 길이를 `fromBuffer` 에서 검증합니다.
2. 클라이언트 제어 채널의 패킷 읽기를 서버와 동일하게 예외 처리로 감쌉니다.
3. 메타 가드 호출부 다섯 곳을 예외 처리로 감싸거나, 게터가 예외 대신 없음을 반환하도록 바꿉니다.
4. 비활성 외부 포트 거절 경로에서 번들을 먼저 설정하거나, 종료 이벤트에서 번들을 옵셔널 체이닝으로 읽습니다.
5. `src/Sentinel.ts:234` 의 `process.kill(1)` 을 `process.exit(1)` 로 교체합니다.
6. 프로세스 전역 예외 처리기를 등록해 마지막 방어선을 둡니다. 다만 이는 위 다섯 항목의 대체재가 아니라 보완재입니다.

### 9.3 단기 (데이터 유실 차단)

1. 캐시 읽기 실패를 성공으로 위장하지 말고 쓰기 실패로 처리합니다. 빈 버퍼 대체를 제거합니다.
2. 파일 캐시 블록 재사용 시 새 식별자를 발급합니다.
3. 로그 회전 정규식을 정상 패턴으로 고칩니다.
4. 소켓 계층 로거에 이름을 부여해 파일 출력을 켭니다.
5. 세션 TTL 기본값을 크게 올리거나 비활성화를 허용하고, 제어 채널 활동을 세션 활동으로 집계합니다.
6. 클라이언트 keepAlive 기본값을 양수로 바꾸고 제어와 데이터 연결에 동일하게 적용합니다.
7. HTTP 파서를 요청용과 응답용으로 분리합니다.
8. chunked 종료 CRLF 와 trailer 를 하류로 전달합니다.
9. Host 치환을 Host 헤더에만 적용합니다.

### 9.4 단기 (검증 체계 복구)

1. PR 트리거에 `npm test` 잡을 추가하고, 공급망 감사의 `paths` 필터를 코드 테스트 잡에서 분리합니다.
2. 배포 파이프라인에 `npm ci` 와 `npm run check` 와 `npm test` 를 게이트로 추가합니다.
3. 공급망 테스트의 실패 시 통과 경로를 제거합니다. 감사 명령의 성공 여부를 먼저 단언하고 실패를 테스트 실패로 승격합니다.
4. 커버리지 계측 범위를 `src` 전체로 넓히고, 현재 값인 라인 64% 와 브랜치 52% 를 기준선으로 삼아 하락을 막습니다.
5. 결함을 고정한 테스트 두 건을 수정과 함께 개정합니다.

### 9.5 중기 (검증 방향 전환)

1. HTTP 모드 터널 왕복, TLS 를 켠 터널 왕복, 다중 클라이언트 동시 접속을 E2E 로 추가합니다. 하네스의 미사용 확장 지점이 이미 준비되어 있습니다.
2. 수십 MiB 페이로드를 터널로 왕복시켜 분할 전송과 재조립과 캐시 스필을 검증합니다.
3. 관리자 UI 에 최소한의 스모크 테스트를 도입합니다. 로그인 해시 계약과 컴포넌트 마운트가 우선 대상입니다.
4. `--forceExit` 를 제거해 자원 누수를 실패로 승격합니다.
5. SRS 추적 매트릭스에 테스트 파일 열을 추가해 요구사항과 검증을 연결합니다.

## 9.6 도입 시점 분류 — 왜 지금 배포본은 잘 도는가

현재 운영 중인 배포본(`1.0.11b`, 커밋 `eac7d0c`)과 개선 브랜치를 대조하면, 결함이 성격이 다른 두 부류로 갈립니다.

**기존 결함은 모두 잠복성입니다.** 특정 트리거 조건이 갖춰져야 드러나므로, 그 조건을 만들지 않는 운영 환경에서는 몇 년이고 문제없이 돕니다.

| 결함 | 드러나는 조건 |
|---|---|
| 원격 종료 경로 (4.5) | 빈 페이로드 세션 종료 패킷 수신 |
| 비활성 포트 예외 (4.6) | 비활성 포트에 접속 |
| `Sentinel` PID 1 시그널 (4.14) | 감시 대상 조회 실패 |
| 로그 회전 미작동 (5.4) | 로그가 디스크를 채울 만큼 장기 운영 |
| HTTP 파서 공유 (4.9) | keep-alive 파이프라이닝 클라이언트 |
| 4GiB 초과 세션 종료 (5.11) | 한 세션으로 4GiB 초과 전송 |

**개선 작업이 새로 만든 결함은 반대로 일상 동작을 즉시 깨뜨립니다.**

| 결함 | 배포본 `1.0.11b` | 개선 브랜치 |
|---|---|---|
| 60초 세션 TTL (5.1) | 기능 자체가 없음 | 도입됨 |
| CSRF 강제 (4.3) | 기능 자체가 없음 | 도입됨 |
| 로그인 레이트리밋 무력화 (4.11) | 기능 자체가 없음 | 도입됨 |
| Svelte 5 마이그레이션 미완 (4.1, 4.2) | 해당 없음 | 미커밋 변경 |
| 배포본 crypto-js 잔존 (4.15) | 해당 없음 | 미커밋 변경 |

즉 배포본이 안정적으로 도는 것은 **결함이 없어서가 아니라 잠복 조건이 충족되지 않았기 때문**이며, 개선 브랜치를 그대로 배포하면 지금까지 없던 증상이 즉시 나타납니다. 관리자 화면이 뜨지 않고, 떠도 설정을 저장할 수 없으며, 유휴 터널이 1분마다 끊깁니다.

**이 사실이 조치 순서를 결정합니다.** 9.1과 9.2를 배포 전 필수 조건으로 두어야 하며, 그전에는 개선 브랜치를 배포해서는 안 됩니다. 기존 잠복 결함(9.3)은 배포본에서도 이미 위험을 안고 있었으므로 같은 릴리스에 함께 처리하는 것이 합리적입니다.

## 10. 확인된 정상 사항

공정을 기하기 위해, 검사 과정에서 정상으로 확인한 사항도 기록합니다.

- 비밀번호 해시 계약은 보존되었습니다. crypto-js 의 SHA-512 와 새 `hash.ts` 의 Web Crypto SHA-512 는 동일한 입력에 동일한 소문자 16진 문자열을 산출합니다. 기존 저장 자격증명과 호환됩니다.
- TypeScript 빌드가 오류 없이 통과합니다.
- 인증 비교 lint 가 65개 파일에서 위반 0건입니다.
- 지난 6개 Phase 가 목표한 보안 경계 자체는 백엔드에 구현되어 있습니다. 문제는 그 경계가 프론트엔드에 반영되지 않은 것이지, 경계가 없는 것이 아닙니다.
- 서버 측 제어 채널 프레이밍에는 예외 처리가 존재합니다. 클라이언트 측에만 없습니다.

## 11. 부록: 검사 방법

8개 영역에 독립 감사자를 배정하고 서로의 결론을 공유하지 않은 채 병렬로 조사했습니다.

| 영역 | 대상 |
|---|---|
| 서버 터널 코어 | `TTTServer`, `TunnelServer`, `ClientHandlerPool`, `ExternalPortServerPool` 등 |
| 클라이언트 | `ClientApp`, `TTTClient`, `TunnelClient`, `EndPointClientPool` 등 |
| 프로토콜 | `CtrlPacket`, `ProtocolV2`, `DataStatePacket`, `BufferReader`/`Writer` 등 |
| HTTP 처리 | `HttpHandler`, `HttpPipe`, `HttpUtil` |
| 관리자 서버 | `AdminServer`, `SessionStore`, `CertificationStore`, `ServerOptionStore` 등 |
| 자원 관리 | `SocketHandler`, `FileCache`, `TCPServer`, 로거, `Sentinel` 등 |
| 테스트 충분성 | `test/` 전체, `jest.config.ts`, CI 워크플로우 |
| 프론트엔드와 빌드 | `admin/src` 전체, `deploy.js`, `package-build.json` |

각 감사자에게는 파일 수정을 금지하고, 모든 지적에 파일과 행 번호 근거를 첨부하며, 확신이 없는 항목은 추정으로 표시하도록 지시했습니다.

보고된 지적 가운데 CRITICAL 전건과 주요 HIGH 항목은 해당 소스를 직접 열어 근거를 재확인했습니다. 일부는 Node 런타임에서 동작을 실측했습니다. 감사자들도 실제 인스턴스를 구동해 재현을 확인한 항목이 다수 있으며, 본문에 그 사실을 명시했습니다.
