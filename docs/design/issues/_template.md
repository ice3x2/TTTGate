# 이슈 초안 작성 규약

이 디렉터리의 `unit0.md` … `unit5.md` 는 GitHub 이슈로 등록될 초안이다. 등록 스크립트가 아래 형식을 기계적으로 파싱하므로 형식을 지킨다.

## 파일 형식

```
## U1-01

**title**: feat(admin): 디자인 토큰·서체·리셋을 app.css 로 이식
**labels**: enhancement, area:frontend, unit:1
**body**:
(본문. 아래 절 구조를 그대로 따른다)

---
```

- 헤딩 `## U<단위>-<두 자리>` 로 시작하고 `---` 로 끝난다.
- `title` 은 커밋 제목 규약과 같다: `feat|fix|test|refactor|docs|chore(범위): 무엇이 바뀌는가`. 단계 표식(`Phase`, `Step`, `U1-01`) 금지. 70자 이내.
- `labels` 는 `enhancement` 또는 `test` 또는 `documentation` 중 하나 + `area:*` 하나 이상 + `unit:N`.

## 본문 절 구조 (모든 이슈 동일, 절 제목 고정)

```
## 목적
한 문단. 이 이슈가 끝나면 무엇이 가능해지는가.

## 배경
현재 코드 상태를 `파일:줄` 로 지목한다. 구현자가 처음 열어야 할 파일 목록을 포함한다.

## 적용되는 결정
프로그램 개요의 D 번호와 한 줄 요약. 구현 중 이 결정과 충돌하면 이슈에 코멘트로 보고하고 결정을 따른다.

## 만들 것
파일별로: 경로, 내보내는 심볼과 시그니처, 동작 규칙. API 라면 메서드·경로·요청·응답 JSON 예시. UI 라면 요소 id·문구·상태 전이.

## 변경할 것
기존 파일별로: 어느 함수의 무엇을 어떻게. 삭제할 파일.

## 하지 말 것
범위 밖 항목과, 흔히 저지르는 오판.

## 수용 기준
먼저 써야 할 테스트를 파일 단위로 나열하고, 각 파일의 케이스를 "…이면 …이다" 형태로 적는다. 이것이 TDD 의 붉은 상태 목록이다.

## 검증 명령
순서대로 실행해 모두 성공해야 하는 명령.

## 선행 · 후행
선행 이슈 ID(등록 후 #번호로 치환됨)와 후행 이슈.

## 근거 문서
설계 문서 경로와 절 번호.
```

## 작성 원칙

1. 구현자는 이 대화의 맥락이 없다. 설계 문서를 읽으라고 시키지 말고 **필요한 계약을 본문에 옮겨 적는다.** 설계 문서 참조는 근거일 뿐이다.
2. "적절히", "필요 시", "등", "알아서" 를 쓰지 않는다. 선택지가 있으면 하나로 정해 적는다.
3. 이슈 하나는 신규·수정 코드 1,500줄 이내(테스트 포함)여야 한다. 넘치면 쪼갠다.
4. 수용 기준의 테스트 케이스는 통과·실패가 기계적으로 갈리게 쓴다(선택자 id, 기대 문자열, 상태 코드, 파일 존재 여부).
5. 커밋 규약(서명 금지, 제목에 단계 표식 금지)을 본문 끝 "검증 명령" 절에 `git log -1 --format=%B` 확인까지 포함해 적는다.
6. 영어 UI 문구는 따옴표로 정확히 적는다(테스트가 그 문자열을 찾는다).
