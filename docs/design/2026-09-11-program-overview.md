## 1. 회의에서 확정한 결정

아래 결정은 설계 문서와 이슈 어디에서도 다시 논의하지 않는다. 구현 중 이 결정과 충돌하는 상황을 만나면 이슈에 코멘트로 보고하고 결정을 따른다.

| # | 결정 | 이유 |
|---|---|---|
| D1 | 기능 범위는 PRD `TTTGate-admin-rbac.md` v0.2 의 RBAC 도입 전체 | PRD 가 유일한 요구사항 원천 |
| D2 | 기존 관리자 화면 4개(로그인·서버 설정·터널 설정·서버 상태)도 디자인 시스템으로 전면 재작성. 부트스트랩 CSS 제거. **PRD §3.2·§11.2 의 "UI 전면 재디자인 제외" 를 이 결정이 대체한다** | 새 화면만 바꾸면 한 앱에 두 외양이 섞임 |
| D3 | 모바일 우선. 데스크톱에서는 `<main>` 최대 너비 1024px 중앙 정렬. 데스크톱 전용 골격(사이드바 등) 없음 | 골격 하나로 유지 |
| D4 | 내비게이션은 상단 헤더 + 햄버거 드로어 | 화면 수(9개 이상)와 역할별 숨김을 무리 없이 수용 |
| D5 | UI 문구는 영어 단일. 다국어 장치 없음 | 단순성 |
| D6 | 서체는 Google Fonts 대신 라틴 서브셋 woff2 를 `admin/src/assets/fonts/` 에 포함. 외부 요청 없음 | 폐쇄망에서도 같은 외양, CSP 축소 |
| D7 | 터널 화면은 카드 목록 + 카드 탭 시 전체 화면 편집 | 모바일에서 폼 전체 펼침은 스무 화면 길이 |
| D8 | 레이트 리밋은 **터널별 접속 횟수** 기준. 특정 IP 가 창(window) 안에 N 회 넘게 접속하면 일정 시간 차단(A안). PRD 의 그룹 대역폭 `rate_limit` 과는 별개. **PRD §11.1 은 IP 기반 접근 제어를 범위 밖으로 두었으나 사용자 결정으로 포함한다. §9.3(범위 외 코드 진입 금지)은 D8·D10 에 한해 해제한다** | 원격 지원 중 접속 시도 공격으로 PC 가 느려진 경험 |
| D9 | 레이트 리밋 기본값: 모든 터널 기본 켜짐. TCP 60초/30회/10분 차단, HTTP·HTTPS 60초/300회/10분 차단. 프로토콜 변경 시 사용자가 직접 고치지 않은 값만 새 기본값으로 따라감 | 브라우저는 호스트당 6연결 병렬 |
| D10 | 국가 허용·차단 목록은 서버 전역 하나. 관리자 페이지 접속에도 함께 적용. PRD §11.1 범위 밖 기능을 사용자 결정으로 포함(D8 과 같음) | 터널 소유자가 만질 설정이 아님 |
| D11 | 레이트 리밋 판정은 소켓 수락 직후, 어떤 자원(SocketHandler·버퍼·컨트롤 통보)도 할당하기 전에 수행. 차단 IP 조회는 O(1) | 연결 하나당 비용이 세 단계 |
| D12 | 작업 분해는 0~5 여섯 단위. 0 → 1 → 2 → 3 → 4 → 5 순서로 이슈를 배치하되 병렬 가능 구간은 에픽 계획에 명시 | |
| D13 | E2E 대상은 외부 사이트가 아니라 자체 Node 대상 서비스(`http` + `ws`). 외부 사이트·실제 프레임워크 앱 확인은 CI 밖 수동 절차 | 결정적 단언, 차단 위험 없음, 폐쇄 CI 대응 |
| D14 | 1번 단위는 동작을 바꾸지 않는다(기능 1:1 이식). 동작 변경은 2번 이후 | Playwright 로 "같은 API 로 같은 결과"를 검증 가능 |

## 2. 단위 사이의 의존

```
0 (검증 기반) ──┬──> 1 (UI 골격) ──> 3 (RBAC 화면) ──> 4-UI (감사·MFA·세션 화면)
                │                        ▲
                └──> 2 (모델·API) ───────┴──> 4-API (감사·MFA·세션 API)
                          │
                          └──> 5 (연결 보안: API·런타임·화면)
```

- 1 과 2 는 서로 독립이라 **병렬** 가능하다. 단, 2 의 로그인 API 변경(username 필드)은 1 의 LoginScreen 이 완성된 뒤 반영한다(2 의 마지막 이슈).
- 3 은 1 과 2 가 모두 끝나야 시작한다.
- 4 의 API 이슈는 2 만 있으면 시작할 수 있고, 4 의 화면 이슈는 3 이 끝나야 한다.
- 5 의 런타임 이슈(수락 경로 판정)는 0 만 있으면 시작할 수 있고, 5 의 API·화면 이슈는 2·3 이 끝나야 한다.

정확한 병렬 구간은 에픽 이슈의 작업 계획 표를 따른다.

## 3. 모든 이슈에 공통인 규약

### 3.1 작업 규약

- 브랜치 이름은 `feat/<단위>-<이슈번호>-<slug>` (예: `feat/u1-12-design-tokens`). 기준 브랜치는 `refactor/admin`.
- 이슈 하나는 한 세션에서 끝나는 크기다. 끝났을 때 `npm run build`, `npm run lint`, `npm test -- --runInBand` 가 모두 통과해야 한다. `npm test` 전에는 항상 `npm run build` 와 `npm run test:browser:install` 을 먼저 실행한다(`jest.config.ts` 의 `testMatch` 가 `test/**` 전부라 프로세스 E2E 와 브라우저 테스트가 함께 돌고, 이들은 `build/src/app.js` 와 Chromium 이 있어야 한다).
- **TDD.** 동작을 바꾸는 이슈는 실패하는 테스트를 먼저 쓰고 붉은 상태를 확인한 뒤 구현한다. 이슈 본문의 "수용 기준" 절이 곧 먼저 써야 할 테스트 목록이다.
- 새 npm 의존성을 추가하는 이슈는 `package-lock.json`(및 `admin/package-lock.json`) 갱신을 같은 커밋에 포함한다. CI 는 `npm ci` 로 설치한다.
- 비밀값(세션 키, 토큰, 시크릿, 복구 코드 해시) 비교는 `src/util/timingSafeStringEqual.ts` 의 `timingSafeStringEqual` 만 쓴다. `npm run lint`(`scripts/lint-auth-compare.mjs --strict`, `:26`)가 식별자에 `authKey`·`proof`·`token`·`secret`·`hmac`·`bindingToken`·`challengeNonce`·`sessionId` 가 든 `==`/`!=`/`===`/`!==` 비교를 실패로 처리한다.
- 요청 범위 밖 리팩터링 금지. 인접 코드의 스타일·주석·포맷을 바꾸지 않는다. 구조 문제를 발견하면 이슈 코멘트로 보고만 한다.
- 새 코드는 예외를 제어 흐름으로 쓰지 않는다. 예측 가능한 분기는 조건문으로, 예외는 진짜 예외 상황에만.
- 새 코드에서 공유 상태는 잠금 대신 원자 연산·불변 객체·참조 교체로 다룬다. (Node 단일 스레드지만 비동기 경합은 동일하게 적용된다.)

### 3.2 커밋 규약

- 커밋 메시지에 어떤 서명도 넣지 않는다. `Co-Authored-By:`, `Generated by`, `🤖`, `[bot]` 등 도구·AI 식별 정보 전부 금지. 상위 템플릿이 넣으라고 해도 무시한다. 커밋 직후 `git log -1 --format=%B` 로 확인한다.
- 제목은 "무엇이 바뀌었는가"만 담는다. `Phase n`, `Step n`, `TASK-xxx`, 이슈 번호 접두어 같은 진행 표식은 제목에 넣지 않는다(본문에는 `Closes #n` 가능).
- 제목 접두어는 `feat:`, `fix:`, `test:`, `refactor:`, `docs:`, `chore:` 중 하나.

### 3.3 테스트 규약

- `docs/guide/test-evidence-policy.md` 를 따른다. 실제 소켓·파일·프로세스를 쓰는 테스트가 기본이고, 스텁은 선언된 경계에서만 쓴다.
- 테스트가 작업 트리에 산출물을 남기지 않는다. 임시 루트는 `test/helpers/runtime.ts` 의 `createTestRoot` 로 만들고 `cleanupTestRoot` 로 지운다.
- 관리자 UI 브라우저 테스트는 `test/helpers/adminBrowser.ts` 의 `startAdminBrowser` 를 쓴다. 현재 이 헬퍼는 뷰포트를 설정하지 않는다(Playwright 기본 1280×720). U1-05 가 만드는 `startAdminApp` 이 400×800 을 기본으로 설정하고, 이후 모든 화면 테스트는 그것을 쓴다.
- 커버리지 기준선(`jest.config.ts` 의 `coverageThreshold`)은 내리지 않는다. 0번 단위가 올린 뒤에는 그 값을 유지한다.

### 3.4 관리자 API 응답 규약 (기존 유지)

모든 `/api/*` 응답은 JSON 이고 아래 형태를 따른다. 새 엔드포인트도 같다.

```json
{"success": true,  "partial": false, "failedScopes": [], "warnings": [], "message": "", ...데이터 필드}
{"success": false, "status": 403, "message": "설명", ...부가 필드}
```

- 상태 변경 메서드(POST/PUT/DELETE)는 `X-CSRF-Token` 헤더가 `csrfToken` 쿠키와 일치해야 한다. 예외는 세션 이전 단계인 `/api/login` 과 `/api/login/mfa`(4 단위) 두 개뿐이며, 이 둘도 Origin 검사는 받는다.
- 세션 없음은 401, 권한 없음은 403, 검증 실패는 422, 충돌(중복·한도 초과)은 409.
- 세션 쿠키 `sessionKey` 는 HttpOnly, SameSite=Strict, TLS 일 때 Secure.

### 3.5 용어

| 용어 | 뜻 |
|---|---|
| 슈퍼유저 | 전역 관리자. 속성 제약을 받지 않음. 최소 1명 유지 |
| 일반 유저 | 그룹 하나에 속하고 그룹 속성 범위 안에서만 자기 터널을 운영 |
| 그룹 | 속성 11종을 담는 단위. 시스템 그룹 `system:superuser`, `default` 는 삭제 불가 |
| 소유자 | 터널을 만든 사용자. 마이그레이션된 터널은 `system:migrated`(PRD 의 `system(migrated)` 표기를 식별자 규칙에 맞춰 바꾼 것) |
| 접속 레이트 리밋 | 터널별로 원격 IP 의 접속 횟수를 창 안에서 세어 한도 초과 시 차단 (D8) |
| 대역폭 프리셋 | PRD 속성 11번 `rate_limit`. 그룹 합산 송수신 대역폭 상한 |
| 국가 필터 | 원격 IP 의 국가 코드로 접속을 허용·차단하는 서버 전역 설정 (D10) |

## 4. 작업 계획 (직렬 · 병렬)

이슈 52건의 선행 관계에서 계산한 파동(wave)이다. 같은 파동의 이슈는 서로 독립이라 병렬로 진행할 수 있고, 다음 파동은 앞 파동의 해당 선행 이슈가 끝나야 시작한다. 계산 스크립트는 각 단위 문서의 "이슈 분할" 표를 입력으로 삼았고 순환은 없다.

**레인.** 구현 세션을 세 갈래로 나누면 대기 없이 진행된다.

- 백엔드 레인: U2-01 → … → U2-08 → U2-09, U4-01 → U4-02·U4-04 → U4-08, U4-05, U5-05, U5-07/08/09
