IP를 영구 차단합니다

관리자가 IP 주소나 대역을 직접 차단 목록에 넣으면, 서버를 다시 시작해도 그 주소의 접속을 계속 막습니다. 레이트 리밋에 걸린 IP는 버튼 하나로 이 목록에 옮길 수 있습니다.

02방식 선택

"영구 차단"을 만드는 방법은 두 가지입니다. 이 문서는 B안을 권장합니다.

A. 차단 시간에 "영구" 추가 권장 안 함

터널의 레이트 리밋 설정에서 차단 시간으로 "Permanent"를 고르게 합니다.

  • 설정 하나만 늘어납니다.
  • 자동 판정으로 영구 차단이 걸립니다. 회사·통신사 NAT 뒤의 정상 사용자도 한 번 몰리면 계속 막힙니다.
  • 차단 표의 상한(포트당 10,000개)이 영구 항목으로 차면 새 차단을 남기지 못합니다. 지금 코드는 "모든 차단은 언젠가 끝난다"를 가정합니다.
  • 터널마다 따로 막으므로, 같은 공격자를 터널 수만큼 막아야 합니다.

B. 관리자 차단 목록 권장

관리자가 IP나 대역을 직접 넣는 목록을 둡니다. 레이트 리밋 차단 행에는 "Block permanently" 버튼을 둡니다.

  • 사람이 확인한 주소만 영구로 막습니다. 자동 판정은 지금처럼 일시적입니다.
  • 한 번 넣으면 모든 터널에 적용됩니다. 필요하면 터널 하나로 좁힐 수 있습니다.
  • server.yaml에 저장되므로 다시 시작해도 남습니다. geo 필터와 같은 방식입니다.
  • Security 화면에 카드 하나와 API 세 개가 늘어납니다.
B안을 고르면 레이트 리밋 설정은 바꾸지 않습니다. 사용자는 "자동 차단은 잠시, 직접 막은 것은 계속"이라는 한 가지 규칙만 기억하면 됩니다.

"Block permanently"를 누르면 확인 창을 띄운 뒤 그 주소를 위 목록에 "All tunnels"로 넣고, 이 행의 일시 차단은 풉니다.

사용 흐름

  1. 직접 넣기: 주소나 대역을 쓰고 Block을 누릅니다. 서버가 확인해서 형식이 틀리면 입력란 아래에 이유를 보여 줍니다.
  2. 일시 차단에서 옮기기: 레이트 리밋 표에서 "Block permanently"를 누릅니다. 확인 창에는 주소와 "모든 터널에서 계속 막습니다"를 보여 줍니다.
  3. 풀기: Unblock을 누르면 확인 창 없이 바로 풉니다. 실수로 풀어도 다시 넣으면 되므로 마찰을 줄입니다. 결과는 토스트로 알립니다.
자기 잠금 방지: 차단 목록은 관리 화면 포트에 적용하지 않습니다(9장 질문 3). 관리자가 실수로 자기 주소를 넣어도 관리 화면에 들어와 풀 수 있습니다.

04판정 순서

터널 연결이 들어오면 AdmissionController.admit이 아래 순서로 판정합니다. 차단 목록은 가장 앞에서 봅니다. 그래야 비용이 큰 국가 조회 전에 거절하고, 영구 차단한 주소가 레이트 리밋 카운터를 쓰지 않습니다.

주소 대조는 Node 내장 net.BlockList(addAddress·addSubnet·check)를 씁니다. BlockList는 IPv4 주소를 IPv6 규칙(IPv4-mapped 대역)과도 비교합니다. 그래서 규칙을 IPv4·IPv6용으로 나눠 두고, 주소는 같은 종류의 규칙과만 비교합니다. 목록이 바뀌면 새 규칙을 만들어 참조만 바꿉니다.

05요구사항

IEEE 29148 형식으로 씁니다. 이슈 본문에도 같은 내용을 옮깁니다.

REQ-1서버는 관리자가 등록한 차단 목록에 든 주소의 터널 연결을 거절해야 한다(shall).
  • AC-1IPv4 주소 203.0.113.7을 넣으면 그 주소의 TCP·HTTP·HTTPS 터널 연결은 모두 거절된다. 다른 주소는 영향이 없다.
  • AC-2CIDR 198.51.100.0/24를 넣으면 198.51.100.0 ~ 198.51.100.255가 거절된다.
  • AC-3IPv6 주소와 대역(2001:db8:1::/48)도 같게 동작한다. IPv4-mapped 주소(::ffff:203.0.113.7)로 들어와도 IPv4 항목에 걸린다. 16진수 표기(::ffff:cb00:7107)로 넣어도 IPv4로 저장한다. IPv6 대역(예: ::/8)은 IPv4 연결을 막지 않는다.
  • AC-4거절 사유는 ip-blocklist이다. 거절은 기존 거절 집계 로그(DenialAggregator)에 남고, 레이트 리밋 카운터와 국가 조회 수를 늘리지 않는다.
REQ-2차단 목록은 서버를 다시 시작하거나 터널을 다시 만들어도 유지되어야 한다(shall).
  • AC-1목록은 server.yaml의 connectionSecurity.blocklist에 저장된다. 서버를 다시 시작한 뒤에도 같은 주소가 거절된다.
  • AC-2터널을 저장하거나 외부 포트를 바꿔 리스너를 새로 만들어도 차단은 유지된다.
  • AC-3저장된 항목 중 형식이 틀린 것은 시작할 때 건너뛰고 경고 로그를 남긴다. 나머지 항목과 서버 시작은 영향을 받지 않는다. 건너뛴 항목은 다음 저장 때 파일에서도 빠지며, 경고에 그 사실을 적는다.
REQ-3항목은 모든 터널 또는 터널 하나에 적용되어야 한다(shall).
  • AC-1"All tunnels" 항목은 지금 있는 터널과 나중에 만드는 터널 모두에 적용된다.
  • AC-2포트를 고른 항목은 그 터널의 연결만 거절한다. 그 터널의 외부 포트를 바꾸면 항목도 새 포트로 옮기고, 터널을 지우면 항목도 지운다. 옮기거나 지우는 동안에도 옛 리스너가 멈출 때까지 그 포트에서 계속 막는다. 터널이 없는 포트에는 항목을 넣을 수 없고, 설정 파일에 그런 항목이 있으면 시작할 때 경고와 함께 뺀다.
  • AC-3관리 화면 포트와 제어 포트(클라이언트 접속)에는 적용하지 않는다.
REQ-4관리자는 Security 화면에서 항목을 보고, 넣고, 풀 수 있어야 한다(shall).
  • AC-1각 항목은 주소(또는 대역), 적용 범위, 메모, 넣은 시각, 넣은 사용자를 보여 준다.
  • AC-2틀린 주소, 0.0.0.0/0·::/0·::ffff:0:0/96처럼 모든 주소를 덮는 대역, 이미 목록에 있는 주소(적용 범위가 달라도 같다), 200자를 넘는 메모는 저장하지 않고 이유를 보여 준다. 중복이면 기존 적용 범위를 함께 보여 준다.
  • AC-3항목 수 상한은 1,000개다. 상한에 이르면 Block 버튼을 끄고 이유를 보여 준다.
  • AC-4넣거나 풀면 바로 적용된다. 서버를 다시 시작할 필요가 없다.
  • AC-5이 기능은 security:manage 권한(슈퍼유저)만 쓸 수 있다. 일반 사용자의 요청은 403을 받는다.
REQ-5레이트 리밋 차단 행에서 그 주소를 차단 목록으로 옮길 수 있어야 한다(shall).
  • AC-1"Block permanently"를 누르고 확인하면 그 주소(IPv6는 표에 보인 /64·/48 대역)가 "All tunnels" 항목으로 들어가고, 메모에는 출처 포트가 들어간다. 그 주소가 포트 하나에만 걸린 항목으로 이미 있으면 그 항목을 "All tunnels"로 넓힌다.
  • AC-2같은 동작에서 그 행의 일시 차단을 푼다. 표에서 행이 사라진다.
  • AC-3이미 "All tunnels"로 목록에 있는 주소이면 새로 넣지 않고 "already blocked"를 알린다. 그 주소는 이미 영구 차단되어 있으므로 그 행의 일시 차단은 풀고, 그 사실을 감사 로그에 남긴다.
REQ-6넣기와 풀기는 감사 로그에 남아야 한다(shall).
  • AC-1넣으면 security_block_added, 풀면 security_block_removed 이벤트가 남는다. 대상 id는 주소이고, detail에는 적용 범위와 메모가 들어간다.
  • AC-2개별 거절은 감사 로그에 남기지 않는다. 기존 거절 집계와 같은 방식이다.

06데이터와 API

저장 형식 (server.yaml)

connectionSecurity:
  geo: { ... }            # 지금과 같음
  blocklist:
    - address: 198.51.100.0/24
      port: null           # null = All tunnels, 숫자 = 그 외부 포트만
      note: Scanner range
      createdAt: 1793145600000
      createdBy: admin

지금 PUT /api/security/geo는 connectionSecurity 전체를 덮어씁니다. 차단 목록이 함께 지워지지 않도록 geo 저장은 geo만 바꾸게 고칩니다.

API (모두 security:manage)

요청동작감사
GET /api/security/blocklist항목 목록과 상한을 돌려준다.—
POST /api/security/blocklist{address, port?, note?, fromBan?: {port, ip}}로 하나를 넣는다. fromBan이 있으면 그 일시 차단을 함께 푼다. 잘못된 입력은 422, 중복은 409. 중복이어도 fromBan의 주소가 이미 "All tunnels"로 막혀 있으면 그 일시 차단은 푼다.security_block_added
DELETE /api/security/blocklist/:address하나를 푼다. 주소는 URL 인코딩한다(/ 포함).security_block_removed

07검증 계획

테스트를 먼저 쓰고 실패를 확인한 뒤 구현합니다.

  • 단위: 주소 정규화와 대조(IPv4, IPv6, CIDR, mapped, 틀린 입력), 입력 검증(전체 대역, 중복, 상한), 판정 순서(차단 목록 거절이 카운터를 늘리지 않음).
  • 관리 API: 넣기·풀기·목록, 권한 403, 감사 이벤트, geo 저장 뒤에도 목록이 남는지.
  • 컴포넌트·E2E: 실제 터널에서 차단 주소 거절, 서버를 다시 시작한 뒤 유지, 리스너를 새로 만든 뒤 유지.
  • 관리 화면: 카드 표시, 입력 오류 표시, "Block permanently" 흐름(목록 추가와 일시 차단 해제).

08범위 밖

  • 레이트 리밋 일시 차단을 디스크에 저장하는 것 (지금처럼 다시 시작하면 풀립니다)
  • 만료일이 있는 수동 차단, 외부 차단 목록 파일·URL 가져오기
  • 허용 목록(이 주소만 접속 허용)
  • 일반 사용자가 자기 터널에만 차단을 거는 기능

09확인할 사항

2026-10-29에 사용자가 네 질문 모두 권장안(초록 점)으로 정했습니다.

  1. 1. 방식 권장안으로 결정
    • B. 관리자 차단 목록 + "Block permanently" 버튼
    • A. 차단 시간에 "영구" 추가
    • A와 B 둘 다
  2. 2. 이미 연결된 세션 권장안으로 결정
    • 새 연결만 거절하고, 이미 맺은 연결은 그대로 둔다 (레이트 리밋 차단과 같음)
    • 넣는 즉시 그 주소의 기존 연결도 끊는다
  3. 3. 관리 화면 포트에도 적용 권장안으로 결정
    • 적용하지 않는다 (관리자가 자기를 잠그지 않음)
    • 적용하되, 요청한 관리자 자신의 주소는 넣지 못하게 막는다
  4. 4. 항목 수 상한 권장안으로 결정
    • 1,000개
    • 10,000개
